    "@liqui-design": "https://liqui.design/r/{name}.json"
  }

```

```

## Usage

```tsx
import { Progress, ProgressLabel, ProgressTrack, ProgressValue } from '@/components/ui/progress';
```

```tsx
<Progress value={68}>
  <div className="flex items-baseline justify-between">
    <ProgressLabel>Rendering</ProgressLabel>
    <ProgressValue />
  </div>
  <ProgressTrack />
</Progress>
```

`ProgressTrack` renders the indicator itself. Unlike
[`SliderTrack`](/docs/components/slider), which has thumbs to place inside it,
there is nothing else that can go in a progress bar — so the part you would
otherwise have to remember is not yours to forget.

`ProgressValue` formats through `Intl.NumberFormat` and takes a render function
for the cases that are not a percentage:

```tsx
<ProgressValue>{() => 'Done'}</ProgressValue>
```

## Indeterminate

<ComponentPreview name="progress-indeterminate" />

`value={null}` is Base UI's indeterminate state. It stops writing an inline
width, which is what lets the component's own classes take over:

```tsx
'data-[indeterminate]:w-full data-[indeterminate]:animate-pulse';
```

A fill across the whole track that breathes, rather than a bar sweeping across it.
The sweep is the more familiar idiom and it is deliberately not here: it needs a
`@keyframes` block, and a registry item is one file dropped into your project —
a component that silently depends on CSS you were never given is worse than one
that uses an animation Tailwind already ships. If you want the sweep, add the
keyframes to your stylesheet and swap the class:

```css title="globals.css"
@keyframes progress-sweep {
  from {
    translate: -100% 0;
  }
  to {
    translate: 400% 0;
  }
}
```

```tsx
'data-[indeterminate]:w-1/4 data-[indeterminate]:[animation:progress-sweep_1.4s_ease-in-out_infinite]';
```

## Notes

### The fill is paint, not a lens

[Slider](/docs/components/slider) puts the glass on the thumb because the thumb
is what moves. A progress bar also has something that moves, and it still does
not get the lens — the difference is *how* it moves.

The displacement map is keyed on the surface's size and cached in a 48-entry
LRU. A thumb slides at one size, so a whole drag reuses a single map. A fill
grows: a refracting fill would ask for a new map on every frame and evict every
other surface's map on the way past, and an unrelated popup would pay to
regenerate the next time it opened — because a download finished. It is the same
cache that makes [tabs](/docs/components/tabs#why-the-tabs-are-flex-1) keep
their pill one width.

So the fixed box keeps the lens, and the fill is the accent, solid:

```tsx
'bg-[var(--lq-accent)]';
```

The same paint as [Slider](/docs/components/slider)'s fill and a checked
[Switch](/docs/components/switch), so a themed accent reads as one colour across
the page.

### Why not a translucent wash

It was one, at 78%, so the glass would show through the filled part. What
showed through was the tint: the bar came out a paler, greyer cousin of the
accent next to every other control, and on a dark theme a different colour
altogether. A theme's accent has to arrive as itself, so the fill is paint and
the lens shows in the part still to go.

The fill is content, so it sits above the specular layer and covers it. The
rim's hairline is redrawn along its top edge so it still reads as sitting in
the groove.

### Sizing

Bezel is a fraction of the box, and the constraint on a bar is its *height*:

```tsx
const TRACK_GLASS = { radius: 5, blur: 1, refraction: 18, bezel: 4 };
```

The bar is 10px, Apple's medium progress bar, and four px of bezel on it
already meets in the middle. Make the bar
shorter and the numbers have to come down with it or the whole thing smears into
one gradient; make it taller and `radius` should go to half the height, or the
map's corners stop matching the corners the element is drawn with.
